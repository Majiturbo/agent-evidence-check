# 0002 产品重定义：第一版做部署核对，不做值层面的前提规则库

- 状态：已接受（看案例之前写了问题陈述；案例写在同一次提交里，作为证据附录，不改停止条件）
- 日期：2026-11-11
- 关联：`docs/cases/`；`docs/judgments.md`

## 背景

用户澄清了真实痛点：不是「消息里的 Q5 / 日期写错了」，而是 Agent
1. 在方向错误或有更近的路时仍照指令往下做；
2. 陷入语义修补循环（自评「改好了」、用户持续否定）；
3. 部署时本地与线上不一致、热修不说清、多工具并行时互相冲掉改动。

值层面的确定性检查（日期 / Q5 / 路径格式）测不到这些问题。否掉的是
「每条请求都做语义拦截」；它没有否掉「不可逆动作前的确定性核对」或
「信号触发后的第三视角」。

## 产品一句话

**Agent 说出的每个判断都要有证据。**「这个方向对」「改好了」「已上线」都算判断。

三个模块（按优先级）：

| 模块 | 触发 | 判断 | 默认动作 | v0.1 |
|---|---|---|---|---|
| **部署核对** | 部署前 / 后 | 纯规则（git + 已配置的部署单元） | 不可逆步骤打断 | **先做** |
| 循环跳脱 | 同文件连改 + 用户连续否定 + 自评落差 | 规则触发，LLM 列出其他做法类别 | Agent 自停并带选项 | 路线图 |
| 方向审查 | 项目开头、转折点 | LLM 第三视角 | 卡片，默认不阻止 | 路线图 |

## 为什么第一版是部署核对

1. **全是事实核对**，不需要 LLM，绕开审计 §5 的误报率争议。
2. **证据最硬**：多工具共用工作区时，「部署前 stash 无关改动」可复现；
   有消费方仓库留下数月未恢复的 stash，以及未跟踪文件只存在于 stash、后来确认永久丢失的样本
   （见 `docs/cases/cross-tool-stash.md`，已脱敏）。
3. **跨工具**：冲突发生在两个 Agent 产品共用同一工作目录时；
   单一 IDE 插件管不到对方，仓库级检查才管得到。这是开源的正当理由。
4. **更近的路也写进产品**：首选建议是「各用 git worktree / 分支，经 CI 部署」；
   检查器是 Agent 仍从本地直推时的兜底，不是取代正规流程。

## v0.1 范围（部署核对）

要做：

- 一个入口 `check(event) → verdict`，事件至少包括 `pre-deploy` / `post-deploy`。
- 封闭检查 id（只能选，不能由模型造名字）：
  - `dirty_tree`：工作区有未提交改动 → 失败（**禁止 stash / checkout 清场**）
  - `unpushed`：要部署的提交不在远程跟踪分支上 → 失败
  - `deploy_from_commit`：部署源必须是明确的 git SHA，不是「当前工作区」
  - `units_declared`：项目配置了部署单元列表（如 `api_image`、`admin_static`）
  - `units_match`（post）：每个单元的线上版本与目标 SHA / 产物指纹一致
  - `hotpatch_drift`：线上文件与 git 树不一致 → 标记为热修，要求补提交
- 输出统一成既有的澄清卡片形状，并转接 MCP elicitation / AG-UI interrupt（契约复用，不自创传输格式）。
- 一个框架转接器（Cursor hook 或等价 before-shell 钩子）：拦截含 `ssh`/`scp`/`rsync`/`docker compose`/`kubectl` 等部署命令的 shell。
- 用户可外挂自定义检查。
- README 用真实案例开头，不编 demo 数字；写明「正例含合成变异时」的限制（若有）。

不做：

- 值层面的日期 / 季度 / 路径格式规则库，以及为它服务的会话导出 / 标注页 / 私有语料。
- 「一键修复对方工具造成的冲突」。
- 宣称能替代 CI / GitOps。
- 每条消息的语义前提拦截。

（方向审查、循环跳脱、完成证据后来作为显式 CLI/MCP 进入 v0.1，见 `0004`；仍不进 shell 钩子、不读对话。）
